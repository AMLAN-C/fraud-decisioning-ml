# PaySim data dictionary and modeling frame

## Source and use

- **Dataset:** Synthetic Financial Datasets for Fraud Detection (PaySim), CSV subset `PS_20174392719_1491204439457_log.csv`.
- **Source:** [Kaggle dataset by ealaxi](https://www.kaggle.com/datasets/ealaxi/paysim1).
- **License listed on Kaggle:** Creative Commons Attribution-ShareAlike 4.0 International (CC BY-SA 4.0). Attribute the dataset and share adaptations under the same license. Do not redistribute the raw CSV in this repository: it is about 494 MB, and the project README keeps raw data out of Git history.
- **Citation:** E. A. Lopez-Rojas, A. Elmir, and S. Axelsson, “PaySim: A financial mobile money simulator for fraud detection,” 28th European Modeling and Simulation Symposium (EMSS), 2016. See the [PaySim project](https://github.com/EdgarLopezPhD/PaySim) for the simulator and citation details.
- **Limitations:** Synthetic transactions generated by a simulator informed by aggregated private transaction data. They are not real customer records and do not establish performance on a live payment system. The sample represents about one simulated month, has severe class imbalance, and offers coarse hourly ordering rather than an exact authorization timestamp.

## Dataset shape and audit

Audited locally from the downloaded CSV in chunks on 2026-11-04.

- **Rows:** 6,362,620
- **Columns:** 11
- **Time coverage:** `step` 1–743; the dataset documentation describes steps as hourly simulation units.
- **Unit:** One simulated mobile-money transaction.
- **Missing values:** None in the audited columns.
- **Exact duplicate rows:** 0 repeated full-row hashes in the audit.
- **Positive label:** `isFraud = 1` for 8,213 rows (about 0.129%); `0` for 6,354,407 rows.
- **Existing rule flag:** `isFlaggedFraud = 1` for 16 rows. It is a separate legacy rule indicator, not the modeling target.
- **Transaction types:** `PAYMENT` 2,151,495; `CASH_OUT` 2,237,500; `CASH_IN` 1,399,284; `TRANSFER` 532,909; `DEBIT` 41,432.

| Column | Type | Meaning / use at prediction point |
|---|---|---|
| `step` | integer | Hourly simulation step; use for forward-in-time splitting and as a coarse time feature. |
| `type` | category | Transaction type; available at transaction decision time. |
| `amount` | numeric | Transaction amount; available at transaction decision time. |
| `nameOrig` | identifier | Simulated origin account ID; useful only for linking history, exclude as a direct feature. |
| `oldbalanceOrg` | numeric | Origin balance before transaction; candidate feature, subject to availability assumptions. |
| `newbalanceOrig` | numeric | Origin balance after transaction; exclude as post-transaction leakage. |
| `nameDest` | identifier | Simulated destination account ID; useful only for linking history, exclude as a direct feature. |
| `oldbalanceDest` | numeric | Destination balance before transaction; candidate feature, subject to availability assumptions. |
| `newbalanceDest` | numeric | Destination balance after transaction; exclude as post-transaction leakage. |
| `isFraud` | binary | Simulator's fraud outcome label; target, known only after the simulated transaction outcome. |
| `isFlaggedFraud` | binary | Existing rule flag; exclude from the first model to avoid rule leakage and measure the model independently. |

## Modeling question and prediction point

At the simulated transaction authorization point, can a fraud-risk model rank transactions for approve, review/step-up, or decline so that it captures more simulated fraud at a stated review capacity or approval rate while limiting false declines? Treat `isFraud` as a post-event outcome label. For the first prototype, assume `step`, `type`, `amount`, and pre-transaction balances are available before the decision; exclude post-transaction balances, the existing rule flag, and raw account identifiers. Validate these assumptions before interpreting metrics.

## Validation and leakage notes

- Use a forward-in-time holdout on `step`; the starter `init.py` reserves the latest 20% of observed steps when possible.
- `step` is coarse and only spans one simulation, so temporal results are dataset-specific, not evidence of long-term or live-system performance.
- Exclude `newbalanceOrig` and `newbalanceDest` because they describe post-transaction states.
- Exclude `isFlaggedFraud` from the first model because it is a pre-existing rule outcome and would make independent model performance hard to interpret.
- Preserve `nameOrig` and `nameDest` for future history/velocity feature construction only if those histories can be computed without crossing the time split; do not use the raw IDs as model features.
